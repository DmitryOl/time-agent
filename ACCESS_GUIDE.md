# Управление доступом: обновление README

Добавьте этот раздел в серверный README вместе с изменениями app/main.py и app/storage.py.
Текущая редакция проекта может отличаться: не заменяйте README целиком.

## Доступ и история

- TG_ALLOWED_USER_ID задаёт ID единственного администратора, должен быть положительным числом.
- Новый человек пишет боту в личные сообщения `/start` и попадает в ожидающие. Самостоятельной регистрации с выдачей доступа нет.
- Администратор видит ожидающих `/users pending`, активных `/users active`, лишённых доступа `/users revoked`. Добавьте номер страницы после статуса для следующей десятки.
- `/grant ID` разрешает доступ человеку, который уже обращался к боту; `/revoke ID причина` отзывает доступ, но не удаляет записи. Команды администратора работают только в личных сообщениях.
- `/userentries ID [active|archive|all] [страница]` показывает записи выбранного человека. `/accesslog ID [страница]` показывает историю разрешений и отзывов, включая причины и время.
- После повторного разрешения доступа пользователю с историей нужно выбрать `/continue` либо `/newstart CONFIRM`. До выбора можно смотреть `/history`.
- `/newstart CONFIRM` переносит все текущие записи в архив; ни текст, ни дата создания не стираются. Архив доступен через `/archive [страница]`. `/list [страница]` показывает только текущие записи.
- Чужие записи и команды управления пользователями недоступны обычному пользователю. Бот принимает эти команды только в личном чате.
- Автоматическое удаление архивных записей ещё НЕ реализовано; срок хранения будет определён отдельно.
- Подключение персонального Google Calendar и рекомендации ещё НЕ реализованы.

## Выкатка

Перед выкаткой убедитесь, что Dockerfile копирует обе Python-программы из `app/` в каталог запуска контейнера. Проверьте действительную конфигурацию, не подменяя её предположениями.

1. Проверьте актуальный бэкап: успешность службы и имя последней копии. Остановитесь, если проверка неуспешна.
2. Установите `app/main.py`, `app/storage.py`, `tests/test_storage.py` в рабочую ветку; выполните `python -m unittest discover -s tests -v` (тесты используют только стандартную библиотеку). Проверьте `git diff --check` и внесите этот раздел в README.
3. Убедитесь, что обновление образа включает новый `storage.py`. Пересоберите образ и выполните `docker compose up -d --build` с текущим compose-файлом. При первом запуске бот дополнит существующую базу таблицами users/access_events и столбцом entries.archived_at. Старые записи и даты сохраняются.
4. Проверьте `/start`, `/list` и `/users active` от имени администратора. Проверьте `/start` и отказ `/list` от тестового пользователя до `/grant`. Затем протестируйте `/grant`, `/revoke` с причиной и повторное разрешение; для `/newstart CONFIRM` используйте отдельного тестового пользователя.
5. Проверьте `docker compose logs --tail=100 app` (не публикуйте содержимое пользовательских записей), затем `git status`. Применять код к действующей базе только после проверки копии и готового пути восстановления.

Переключение Git назад НЕ отменит миграцию базы; старый код сможет читать исходные таблицы, но не должен использоваться для управления новым доступом. Перед восстановлением из копии остановите бота и убедитесь, что не теряете новые записи.
